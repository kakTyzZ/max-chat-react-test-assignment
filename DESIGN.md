# Design Document: минимальный чат MAX на React

Статус: проектирование. Дата: 2026-09-29. Основание: [тестовое задание](https://drive.google.com/file/d/1Ut39kkIs0QK-swnCsIPJc6pNqVIVGOD2/view).

## 1. Цель и границы

Пользователь открывает сайт, вводит данные своего инстанса GREEN-API, создаёт чат по номеру телефона MAX, отправляет текст и видит текстовый ответ. Продукт должен оставаться простым, похожим по композиции на [веб-чат MAX](https://web.max.ru/): список чатов, открытая переписка, поле ввода и понятные состояния загрузки и ошибки.

Реализуются только личные текстовые переписки. Медиа, группы, звонки, реакции, редактирование, удаление, поиск по истории и полноценная синхронизация всех чатов не входят в обязательный объём. Дополнительные функции допустимы только после выполнения основного сценария.

## 2. Требования задания и критерии готовности

| Требование | Решение | Проверка |
| --- | --- | --- |
| React | SPA на React + TypeScript | Сборка и открытие приложения |
| Данные GREEN-API | Экран подключения: `apiUrl`, `idInstance`, `apiTokenInstance` | Ошибки ввода и соединения отображаются в UI |
| Новый чат по телефону | Нормализация номера, `CheckAccount`, сохранение полученного `chatId` | Чат появляется после успешной проверки |
| Отправка текста | `SendMessage` с `chatId` и `message` | Сообщение отображается с состоянием отправки/ошибки |
| Получение текста | HTTP API: `ReceiveNotification` → обработка → `DeleteNotification` | Ответ попадает в нужный чат один раз |
| Простой интерфейс как в MAX | Двухпанельный десктопный вид и адаптивный узкий вид | Автоматические UI-проверки на двух ширинах |
| Передача результата | GitHub, инструкция запуска, желательно ссылка на сайт | README и ссылки присутствуют |

Приёмочный сценарий: после подключения существующего авторизованного инстанса пользователь создаёт чат с номером, зарегистрированным в MAX, посылает текст, а пришедший текстовый ответ появляется в этой переписке без перезагрузки страницы.

## 3. Важные особенности GREEN-API

- Для запросов нужны **три** параметра из кабинета: `apiUrl`, `idInstance`, `apiTokenInstance`. В задании названы только последние два; поле `apiUrl` нужно для корректного адреса кластера. Источник: [перед началом работы](https://green-api.com/v3/docs/before-start/).
- Инстанс должен быть создан и авторизован в MAX, а входящие уведомления включены. Для HTTP API `webhookUrl` должен быть пустым; конфигурация выполняется в кабинете или через `SetSettings`. Приложение показывает понятную инструкцию при отсутствии входящих, но не меняет настройки инстанса автоматически. Источник: [получение через HTTP API](https://green-api.com/v3/docs/api/receiving/technology-http-api/).
- Номер телефона нельзя считать постоянным ключом переписки. `CheckAccount` возвращает `chatId`, который используется при отправке и сопоставлении входящих сообщений. Документация прямо рекомендует этот путь, когда нужны ответы. Для метода допускаются номера РФ и РБ. Источники: [CheckAccount](https://green-api.com/v3/docs/api/service/CheckAccount/), [идентификатор чата](https://green-api.com/v3/docs/api/chat-id/).
- `SendMessage` принимает текст до 4000 символов и возвращает `idMessage`; ответ метода означает постановку в очередь, а не гарантированную доставку. Источник: [SendMessage](https://green-api.com/v3/docs/api/sending/SendMessage/).
- Очередь входящих уведомлений хранится до 24 часов. После успешной обработки уведомление подтверждается `DeleteNotification` по `receiptId`. Источники: [HTTP API](https://green-api.com/v3/docs/api/receiving/technology-http-api/), [ReceiveNotification](https://green-api.com/v3/docs/api/receiving/technology-http-api/ReceiveNotification/), [DeleteNotification](https://green-api.com/v3/docs/api/receiving/technology-http-api/DeleteNotification/).

## 4. Архитектура

```text
Браузер: React UI
  ├─ подключение / создание чата / отправка
  └─ обновление сообщений через собственный API
             │ same-origin HTTP
             ▼
Небольшой Node.js сервер
  ├─ сессия пользователя и краткоживущие данные чатов
  ├─ один последовательный потребитель очереди на инстанс
  └─ адаптер GREEN-API (CheckAccount, SendMessage, Receive/DeleteNotification)
             │ HTTPS
             ▼
GREEN-API → MAX
```

Технологический стек: React, TypeScript, Vite для клиента; Node.js + TypeScript с небольшим HTTP-фреймворком для сервера; простое хранилище сессии и сообщений. На первом этапе приложение запускается как один процесс/одна реплика. Перед публикацией выбирается хостинг, поддерживающий постоянно работающий сервер: очередь уведомлений нельзя надёжно обрабатывать только в статическом хостинге или краткоживущих serverless-запросах.

Сервер нужен для контролируемого опроса очереди и чтобы токен не попадал в URL запросов браузера и клиентские логи. Пользователь вводит токен один раз через HTTPS. Сервер держит его в памяти сессии, не записывает в БД, файлы или логи. Браузер получает только непрозрачную cookie `HttpOnly`, `SameSite=Lax`, `Secure` на HTTPS. Сессия истекает при бездействии; кнопка «Отключиться» удаляет её. В локальном режиме HTTP флаг `Secure` зависит от окружения.

Для демонстрационного объёма сообщения можно хранить в памяти сервера на время сессии. Это означает, что после перезапуска сервера история исчезнет; UI честно сообщает об этом, а задача не требует долговременного архива. Если понадобится восстановление истории, отдельным улучшением станет метод журнала чата или постоянное хранилище.

## 5. Основные компоненты UI

1. **Подключение.** Поля `apiUrl`, `idInstance`, `apiTokenInstance`; проверка формата, индикатор подключения, краткие сообщения об ошибках. Поле токена скрыто.
2. **Список чатов.** Кнопка «Новый чат», номер/имя, последняя строка текста, время, активный чат и пустое состояние.
3. **Создание чата.** Ввод номера, нормализация пробелов/скобок/дефисов, проверка поддерживаемого формата и `CheckAccount`; явное сообщение, если адресат не найден или сработал лимит проверки.
4. **Переписка.** Шапка с адресатом, список входящих и исходящих текстов с временем, поле ввода, кнопка отправки и видимые состояния `sending`, `queued`, `failed`.
5. **Адаптивность и доступность.** На узком экране список и переписка открываются по очереди; клавиатурная навигация, метки полей, достаточный контраст, читаемые ошибки, область новых сообщений с умеренным `aria-live`.

## 6. Потоки данных

### Подключение

Клиент передаёт параметры серверу. Сервер валидирует HTTPS `apiUrl` и допустимый домен GREEN-API, проверяет доступность/состояние инстанса, создаёт сессию и запускает один цикл чтения уведомлений. Сетевые запросы имеют таймауты. Ошибки авторизации и недоступности отображаются без утечки токена.

### Новый чат

Клиент передаёт номер; сервер нормализует и проверяет его, вызывает `CheckAccount` и создаёт локальную запись с каноническим `chatId`. Повторное создание того же `chatId` открывает существующий чат. Ошибки ограничения частоты и отсутствие аккаунта показываются отдельно.

### Отправка

Клиент отправляет `{chatId, text}`. Сервер проверяет принадлежность чата сессии и длину текста, вызывает `SendMessage`, сохраняет `idMessage` и отдаёт результат. Повторная отправка после сетевого таймаута не выполняется автоматически, чтобы избежать дублей. Неподтверждённая доставка не маркируется как «доставлено».

### Получение

Сервер последовательно вызывает `ReceiveNotification`. Для `incomingMessageReceived` с типом `textMessage` извлекает `senderData.chatId`, `idMessage`, время и текст; сопоставляет чат, сохраняет сообщение с дедупликацией по `idMessage`, затем подтверждает `receiptId` через `DeleteNotification`. Остальные типы уведомлений пропускаются и подтверждаются, чтобы не блокировать очередь. Если обработка или сохранение не удались, подтверждения нет; запись будет получена вновь. Пустой ответ вызывает ограниченную паузу, ошибки сети — экспоненциальную задержку. Опрос прекращается при завершении сессии. Клиент получает обновления собственного сервера (периодический запрос или SSE; выбор по простоте реализации).

Важно: очередь GREEN-API принадлежит инстансу. Одновременное использование того же инстанса другим потребителем может приводить к пропуску уведомлений в этом приложении. Сервер допускает один активный цикл на инстанс и сообщает о конфликте локальных сессий.

## 7. Предлагаемый внутренний API

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/api/session` | Подключить инстанс |
| DELETE | `/api/session` | Отключиться и очистить сессию |
| GET | `/api/session` | Узнать состояние подключения |
| POST | `/api/chats` | Проверить номер и открыть чат |
| GET | `/api/chats` | Список чатов |
| GET | `/api/chats/:chatId/messages` | Сообщения чата |
| POST | `/api/chats/:chatId/messages` | Отправить текст |

Форма ошибок: стабильный код (`INVALID_PHONE`, `INSTANCE_UNAVAILABLE`, `RECIPIENT_NOT_FOUND`, `RATE_LIMITED`, `NETWORK_ERROR`) и безопасное человекочитаемое сообщение. Полные ответы GREEN-API и URL с токеном не отдаются клиенту и не логируются.

## 8. Автоматическая проверка

- Unit: нормализация номера, валидация `apiUrl`, ограничение текста, разбор текстового уведомления, дедупликация.
- Контрактные тесты с подставным GREEN-API: успешный `CheckAccount`, отправка, пустая очередь, текстовый ответ, посторонние уведомления, повторная доставка, ошибка до подтверждения, таймаут/лимит.
- UI-тесты в выделенном headless-браузере: подключение, создание чата, отправка, получение, состояния ошибок, узкий и широкий экран. Реальный токен в автоматические тесты и CI не помещается.
- Сборка, типизация, линтер и тесты выполняются одной командой перед публикацией.

## 9. Риски и решения

| Риск | Подход |
| --- | --- |
| В задании не назван `apiUrl` | Добавить поле с объяснением, где взять адрес |
| Номер не совпадает с `chatId` входящего сообщения | Всегда получать `chatId` через `CheckAccount` |
| API отдаёт успех отправки, но сообщение ещё в очереди | Показывать «поставлено в очередь», не обещать доставку |
| Токен в адресе запросов GREEN-API | Прокси на сервере, очистка логов, без localStorage |
| Потребители конкурируют за одну очередь | Один poller на инстанс, явное ограничение многопользовательского режима |
| Перезапуск сервера сбрасывает историю | Обозначить краткоживущую историю; не обещать архив |
| Лимиты `CheckAccount` и запросов | Не проверять номер на каждый символ, показывать лимит и использовать задержку |

## 10. Вопросы, которые уточняются во время реализации

- Точный формат событий отправки и статусов сверить с примерами API и зафиксировать fixtures.
- Выбрать периодический запрос или SSE после замера простоты и надёжности на выбранном хостинге.
- Определить площадку публикации после готовности серверной части. Публикация желательна по заданию, но обязательны репозиторий и инструкция запуска.
